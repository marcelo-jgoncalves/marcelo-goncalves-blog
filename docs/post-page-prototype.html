Como construir uma arquitetura serverless resiliente na AWS com Lambda, SQS e DLQ

Por Marcelo Gonçalves 14 mai. 2026 12 min de leitura
Em resumo

Arquiteturas serverless permitem escalar do zero ao infinito sem gerenciar servidores. Mas a resiliência depende inteiramente de como você conecta os componentes — uma Lambda mal configurada pode perder mensagens para sempre. Este artigo mostra como combinar Lambda, SQS e DLQs para construir pipelines que falham com elegância.

Por que serverless muda o jogo

Nos últimos cinco anos, o paradigma serverless passou de curiosidade técnica a base de operações de empresas como Airbnb, Coca-Cola e a própria AWS, que hoje processam bilhões de eventos por mês usando AWS Lambda em produção. O modelo elimina o gerenciamento de infraestrutura e cobra apenas pelo que você usa — com granularidade de milissegundos.

Mas serverless não é uma bala de prata. A resiliência depende inteiramente de como você conecta os componentes. Uma função Lambda que falha sem uma fila de mensagens por trás dela pode simplesmente perder o evento — para sempre. É exatamente aqui que o Amazon SQS entra como peça central de qualquer arquitetura event-driven séria.

i
Conceito-chave

Em arquiteturas event-driven, a pergunta mais importante não é "o que acontece quando tudo funciona?" — mas "o que acontece quando algo falha?"

SQS como buffer durável entre componentes

O Amazon SQS (Simple Queue Service) age como um buffer durável entre produtores e consumidores de eventos. Se a Lambda que processa uma mensagem falhar — seja por erro de código, timeout ou throttling — a mensagem volta para a fila automaticamente após o visibility timeout expirar.

A configuração básica envolve três decisões críticas:

  • Visibility timeout — quanto tempo a mensagem fica invisível para outros consumidores enquanto está sendo processada
  • Message retention — por quanto tempo permanece na fila se não for deletada (máximo: 14 dias)
  • Receive count — quantas vezes pode ser recebida antes de ir para a DLQ
terraform 
resource "aws_sqs_queue" "processing" {
  name                       = "event-processing"
  visibility_timeout_seconds = 300  # >= Lambda timeout
  message_retention_seconds  = 86400

  # Mensagens que falharem 3 vezes vão para a DLQ
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.dlq.arn
    maxReceiveCount     = 3
  })

  tags = {
    Environment = "production"
    ManagedBy   = "terraform"
  }
}

Visibility timeout: a regra dos 6×

O visibility timeout precisa ser pelo menos 6× o timeout da Lambda. Isso garante que mesmo em retries internos do AWS SDK, a mensagem não retorne à fila enquanto ainda está sendo processada — gerando processamento duplicado e bugs sutis em produção.

Uma DLQ bem configurada não é sinal de que seu sistema falha. É sinal de que seu sistema é honesto sobre as falhas que inevitavelmente ocorrem em escala.

Dead Letter Queues: o safety net

Uma DLQ (Dead Letter Queue) é simplesmente outra fila SQS que recebe mensagens que falharam além do número máximo de tentativas configurado em maxReceiveCount. É o safety net da arquitetura: nenhuma mensagem é perdida, elas apenas mudam de estado e ficam disponíveis para análise.

!
Cuidado em produção

A retenção máxima da DLQ é também 14 dias. Se ninguém investigar as mensagens nesse período, elas serão permanentemente deletadas. Configure alarmes que falem mais alto do que isso.

O padrão que uso em produção há anos é combinar a DLQ com um CloudWatch Alarm enviando notificações via SNS. Quando qualquer mensagem chega na DLQ, eu quero saber em menos de 5 minutos — antes que o cliente perceba qualquer anomalia.

Investigando mensagens na DLQ

Algumas práticas que tornam o pós-mortem mais rápido:

  1. Inclua sempre um correlation_id nas mensagens, gerado no ponto de origem
  2. Logue cada erro com o messageId antes de deixá-lo falhar
  3. Mantenha um runbook documentando como reprocessar mensagens da DLQ
  4. Configure um job semanal que conte mensagens na DLQ e gere um relatório

Event source mapping na prática

A integração Lambda–SQS é feita via Event Source Mapping. A Lambda poola a fila automaticamente em lotes configuráveis, com suporte nativo a ReportBatchItemFailures — que permite reprocessar apenas as mensagens que falharam, e não o lote inteiro.

Parâmetro Valor recomendado Justificativa
Batch size 10 Balanceia throughput e granularidade de erro
Max concurrency 10–50 Protege sistemas downstream de bursts inesperados
Bisect on error true Isola a mensagem problemática sem perder o lote
Report failures true Reprocessa apenas o que falhou, não o lote inteiro
Maximum batching window 5s Reduz invocações desnecessárias com tráfego baixo

Monitoramento e alertas

Métricas que importam acompanhar em produção:

  • ApproximateAgeOfOldestMessage — sinaliza backlog crescente
  • NumberOfMessagesSent vs NumberOfMessagesDeleted — gap indica perda
  • ApproximateNumberOfMessagesVisible na DLQ — alarme imediato em qualquer valor > 0
  • Lambda Errors e Throttles — sintomas do problema, não a causa
✓
Padrão de produção

Use CloudWatch dashboards com widgets para cada uma dessas métricas, separados por ambiente. Em produção, configure alarmes compostos: ApproximateAgeOfOldestMessage > 60s E Lambda errors > 0 indica problema real, não flutuação normal.

O que aprendi quebrando coisas

Em mais de 10 anos construindo sistemas distribuídos, a lição mais cara que aprendi é simples: sempre assuma que mensagens vão se perder se você não desenhar o sistema para retê-las. SQS + DLQ + alarmes não é overengineering — é o mínimo profissional para qualquer pipeline que processe eventos importantes.

A diferença entre uma arquitetura serverless amadora e uma profissional não está na quantidade de serviços usados. Está em quão honesta ela é sobre o que pode dar errado.
