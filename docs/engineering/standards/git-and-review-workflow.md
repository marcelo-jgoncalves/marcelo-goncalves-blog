# Git, commits, pull requests e revisão

## Branches

- `main`: estado estável, não recebe commit direto.
- `develop`: branch de integração — push aqui dispara o pipeline CD (build → terraform apply → deploy). Onde o trabalho do dia a dia acontece.
- `feature/<descricao>` / `fix/<descricao>`: de vida curta, nascem de `develop`, voltam via PR — para mudanças que atravessam vários componentes, alteram arquitetura/contratos, envolvem segurança, modificam infraestrutura ou têm valor pedagógico/risco relevante.
- Mudanças pequenas, isoladas e de baixo risco podem ser feitas diretamente em `develop`, como já era o padrão do projeto.

GitFlow completo (`release/*`, `hotfix/*`, `support/*`) não foi adotado — resolve um problema de cadência de release versionada que este projeto não tem ainda (sem ambiente de produção). Gatilho para revisitar: produção existir de fato.

## Commits — Conventional Commits

```text
feat: fix: refactor: test: docs: chore: ci: build: perf: security:
```

- um commit deve representar uma unidade lógica;
- não misturar refatoração, funcionalidade e correção sem necessidade;
- mensagem explica a intenção, não só os arquivos alterados;
- evitar mensagens genéricas (`updates`, `changes`, `fix stuff`);
- não registrar conversa, prompt ou contexto de sessão no commit;
- não usar "generated by Claude"/"Co-Authored-By: Claude" — Marcelo pediu para não atribuir autoria de IA no GitHub;
- falhas intermediárias não precisam virar commits permanentes.

### Trailers opcionais para casos do livro

```text
Book-Case: CASE-000
AI-Role: investigation, implementation, test-generation
Human-Decision: descrição curta
Evidence: unit, integration, CI
```

Usar apenas quando acrescentarem rastreabilidade real — não obrigatórios para mudanças rotineiras.

## Preservação seletiva de histórico

Não fazer squash indiscriminado. Em mudanças com valor pedagógico, preservar commits que representem mudança real de modelo/estratégia (teste de caracterização, aplicação da solução, fortalecimento da validação). Pode-se fazer squash de: correções de formatação, typos, ajustes mecânicos, commits `fixup`, tentativas sem valor histórico.

## Pull requests

Abrir cedo em mudanças relevantes, preferencialmente como draft — o PR deve registrar o raciocínio antes do resultado final ser conhecido.

Estrutura recomendada: Contexto, Problema, Hipótese/decisão proposta, Escopo, Fora de escopo, Alternativas consideradas, Riscos, Critérios de aceitação, Obrigações de prova, Alterações realizadas, Evidências, Participação da IA, Decisões e intervenções humanas, Rollback, Documentação relacionada, Estudo de caso relacionado. Nem toda seção precisa ser extensa.

**O PR não duplica o estudo de caso**: PR é revisão e aprovação da mudança; estudo de caso é evolução do raciocínio; ADR é decisão arquitetural vigente; backlog é trabalho pendente. Usar links entre eles.

## Revisão de PR

Verificar: o problema foi realmente resolvido; o escopo foi respeitado; contratos continuam coerentes; testes provam o comportamento pretendido (mocks não escondem diferenças importantes); segurança e permissões consideradas; observabilidade suficiente; rollback possível quando necessário; documentação canônica atualizada; nenhuma abstração ou refatoração oportunista; participação da IA e decisão humana corretamente atribuídas; caso do livro atualizado quando aplicável. A revisão não se limita a estilo e lint.

## Comentários no código

Ver `docs/engineering/standards/code-conventions.md` — mesma regra "why, not what", sem travessão, sem autoria de IA.

## Issues e backlog

- `docs/backlog.md`: fonte canônica do trabalho planejado individual.
- GitHub Issue: quando houver discussão, colaboração ou rastreabilidade externa natural com PR.
- PR: implementação e revisão. Estudo de caso: aprendizado. ADR: decisão vigente.

Quando existir issue, o backlog contém apenas ID e link — nunca a mesma tarefa duplicada em dois lugares.

## Definition of Done

Uma tarefa está concluída quando as obrigações aplicáveis estiverem satisfeitas: implementação concluída; testes proporcionais ao risco; lint/build/validações aplicáveis; segurança verificada; documentação canônica atualizada; contexto operacional atualizado somente se necessário; ADR atualizado quando houver decisão; caso atualizado quando houver captura ativa; PR revisado quando aplicável; evidências registradas; pendências remanescentes encaminhadas ao backlog. Não exigir a suíte completa para toda mudança — exigir a prova adequada ao risco.

## Fluxo recomendado

```text
Backlog ou problema → branch/PR quando necessário → hipótese e critérios de aceitação
→ caso do livro, se aplicável → implementação em ciclos pequenos → evidências e revisão
→ atualização de ADR/documentação → merge → encerramento ou revisão futura do caso
```
