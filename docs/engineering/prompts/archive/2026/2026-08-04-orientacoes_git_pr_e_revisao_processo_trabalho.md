# Orientações complementares para o novo processo de trabalho

## Veredito

A estrutura principal já está planejada:

- fontes canônicas;
- `CLAUDE.md` reduzido;
- contexto operacional separado;
- protocolo de captura;
- template de casos;
- skill;
- integração da skill ao fluxo.

Ainda falta formalizar um padrão para:

- branches;
- commits;
- pull requests;
- revisão;
- comentários no código;
- encerramento do ciclo.

O documento canônico recomendado é:

```text
docs/engineering/standards/git-and-review-workflow.md
```

O `CLAUDE.md` deve conter apenas um resumo e apontar para esse documento.

---

# 1. Branches

Use uma estratégia simples:

- `main`: estado estável;
- `develop`: branch de integração;
- `feature/<descricao>`: mudança funcional ou estrutural relevante;
- `fix/<descricao>`: correção relevante;
- `docs/<descricao>`: documentação relevante;
- `refactor/<descricao>`: refatoração sem mudança funcional.

Mudanças pequenas, isoladas e de baixo risco podem ser feitas diretamente em `develop`.

Use branch e pull request quando a mudança:

- atravessar vários componentes;
- alterar arquitetura ou contratos;
- envolver segurança;
- modificar infraestrutura;
- exigir revisão como unidade;
- possuir valor pedagógico para o livro;
- tiver risco ou rollback relevante.

---

# 2. Commits

Use Conventional Commits:

```text
feat:
fix:
refactor:
test:
docs:
chore:
ci:
build:
perf:
security:
```

## Regras

- um commit deve representar uma unidade lógica;
- não misturar refatoração, funcionalidade e correção sem necessidade;
- mensagem deve explicar a intenção, não apenas os arquivos alterados;
- evitar mensagens genéricas como `updates`, `changes` ou `fix stuff`;
- não registrar conversa, prompt ou contexto de sessão;
- não usar “generated by Claude” no título;
- falhas intermediárias não precisam virar commits permanentes.

## Trailers opcionais para mudanças relevantes

```text
Book-Case: CASE-000
AI-Role: investigation, implementation, test-generation
Human-Decision: descrição curta
Evidence: unit, integration, CI
```

Use trailers apenas quando acrescentarem rastreabilidade real.

---

# 3. Preservação do histórico para o livro

Não faça squash indiscriminado.

Em mudanças com valor pedagógico:

- preserve commits que representem mudanças reais no modelo ou na estratégia;
- preserve o commit que adiciona o teste de caracterização;
- preserve o commit que aplica a solução;
- preserve o commit que fortalece a validação, quando isso formar uma sequência útil.

Pode fazer squash de:

- correções de formatação;
- typos;
- ajustes mecânicos;
- commits `fixup`;
- tentativas sem valor histórico;
- ruído produzido durante revisão.

O objetivo é preservar a evolução técnica, não cada tecla pressionada.

---

# 4. Pull requests

Abra o PR cedo nas mudanças relevantes, preferencialmente como draft.

O PR deve registrar o raciocínio antes que o resultado final seja conhecido.

## Estrutura recomendada

```markdown
# Contexto

# Problema

# Hipótese ou decisão proposta

# Escopo

# Fora de escopo

# Alternativas consideradas

# Riscos

# Critérios de aceitação

# Obrigações de prova

# Alterações realizadas

# Evidências

# Participação da IA

# Decisões e intervenções humanas

# Rollback

# Documentação relacionada

# Estudo de caso relacionado
```

Nem todas as seções precisam ser extensas.

## Regra importante

O PR não deve duplicar o estudo de caso.

- PR: revisão e aprovação da mudança;
- estudo de caso: evolução do raciocínio e aprendizado histórico;
- ADR: decisão arquitetural vigente;
- backlog: trabalho pendente.

Use links entre eles.

---

# 5. Revisão de PR

A revisão deve verificar:

- o problema foi realmente resolvido;
- o escopo foi respeitado;
- os contratos continuam coerentes;
- os testes provam o comportamento pretendido;
- mocks não escondem diferenças importantes;
- segurança e permissões foram consideradas;
- observabilidade é suficiente;
- rollback é possível quando necessário;
- documentação canônica foi atualizada;
- não houve abstração ou refatoração oportunista;
- participação da IA e decisão humana estão corretamente atribuídas;
- o caso do livro foi atualizado quando aplicável.

A revisão não deve se limitar a estilo e lint.

---

# 6. Comentários no código

Comente somente quando o código não consegue expressar adequadamente:

- o motivo de uma decisão;
- uma restrição externa;
- um invariante;
- um comportamento contraintuitivo;
- um trade-off;
- uma condição de segurança;
- uma incompatibilidade de serviço;
- a razão para uma solução aparentemente estranha.

Não comentar:

- o que o código já mostra;
- narrativa da sessão;
- prompt usado;
- autoria da IA;
- histórico completo da decisão;
- TODOs sem vínculo com backlog;
- explicações que pertencem a ADR ou documentação.

Exemplo adequado:

```ts
// DynamoDB rejects empty values for indexed attributes.
// Omit the field instead of persisting an empty string.
```

Exemplo inadequado:

```ts
// Claude changed this after we found a bug in session 42.
```

---

# 7. Issues e backlog

Evite manter a mesma tarefa em dois lugares.

Recomendação:

- `docs/delivery/backlog.md`: fonte canônica do trabalho planejado individual;
- GitHub Issue: usar quando houver discussão, colaboração, rastreabilidade externa ou vínculo natural com PR;
- PR: implementação e revisão;
- estudo de caso: aprendizado;
- ADR: decisão vigente.

Quando criar uma issue, o backlog deve conter apenas o ID e o link.

---

# 8. Definition of Done

Uma tarefa só está concluída quando as obrigações aplicáveis estiverem satisfeitas:

- implementação concluída;
- testes proporcionais ao risco;
- lint, build ou validações aplicáveis;
- segurança verificada;
- documentação canônica atualizada;
- contexto operacional atualizado somente se necessário;
- ADR atualizado quando houver decisão;
- caso atualizado quando houver captura ativa;
- PR revisado quando aplicável;
- evidências registradas;
- pendências remanescentes encaminhadas ao backlog.

Não exigir a suíte completa para toda mudança; exigir a prova adequada ao risco.

---

# 9. Fluxo recomendado

```text
Backlog ou problema
        ↓
Branch/PR quando necessário
        ↓
Hipótese e critérios de aceitação
        ↓
Caso do livro, se aplicável
        ↓
Implementação em ciclos pequenos
        ↓
Evidências e revisão
        ↓
Atualização de ADR/documentação
        ↓
Merge
        ↓
Encerramento ou revisão futura do caso
```

Criar:

```

Para branches, commits, pull requests, revisão e comentários, siga
`docs/engineering/standards/git-and-review-workflow.md`.

Mudanças estruturais, transversais, sensíveis ou pedagogicamente relevantes
devem usar branch curta e pull request.
```
